## 2. Yang berubah, per langkah

### Langkah 1: seeder tidak lagi menimpa data (F1)
- **Masalah:** `npm run db:seed` yang dijalankan ulang menimpa edit pada baris ber-ID seed, tanpa peringatan.
- **Perbaikan:** `src/db/seed.ts` memakai `ON CONFLICT ... DO NOTHING` untuk akun, jenis, obat, inventaris, penyemaian, meja, pemindahan, dan versi sinkronisasi. Saldo awal ditambahkan ke saldo yang ada, tidak lagi menimpanya.
- **Akibat yang perlu diketahui:** seed ulang tidak lagi menyegarkan tanggal data uji. Untuk tanggal baru, hapus file database lokal lalu migrasi dan seed lagi. Hal ini sudah ditulis di `docs/panduan-menjalankan-backend.md`.

### Langkah 2: pencegahan saling timpa antar perangkat (F2)
- **Masalah:** hanya `PATCH /panen` yang punya `expected_version`, jadi dua ponsel bisa saling menimpa diam-diam.
- **Perbaikan:** `PATCH` meja-tanam, kerusakan, penyemaian, pemindahan, inventaris, obat, dan jenis-inventaris kini menerima `expected_version` opsional. Versi yang basi menghasilkan `409 VERSION_CONFLICT` tanpa perubahan apa pun. Logikanya satu tempat, di `executeDomainMutation` (`src/common/sync.ts`).
- **Sengaja dijaga:**
  - Field ini opsional, supaya aplikasi Flutter sekarang tetap jalan.
  - Retry dengan kunci yang sama tetap mengembalikan resi lama, walau versinya sudah bergerak.
  - Baris yang tidak ada tetap `404`.
  - Body yang hanya berisi `expected_version` ditolak `400`.
- **Batasan penting:** masalah ini **belum hilang di aplikasi** sampai Flutter ikut mengirim `expected_version`. Yang selesai baru sisi backend.

### Langkah 3: satu meja rusak tidak menjatuhkan seluruh daftar (F3)
- **Masalah:** satu baris tidak konsisten membuat `GET /meja-tanam` gagal total, dan API tidak bisa dipakai untuk memperbaikinya.
- **Perbaikan:** respons meja mendapat field baru `saldo_valid`. Daftar tetap `200`; meja rusak ditandai `saldo_valid: false` dengan `kapasitas_tersedia: 0`.
- **Tetap ketat:** `GET /meja-tanam/:id` tetap `409 TABLE_BALANCE_INVALID`. `PATCH` kini bisa memperbaiki meja rusak, tetapi hanya kalau hasilnya valid; kalau tidak, seluruh perubahan dibatalkan.

### Langkah 4: `X-Client-Id` pada update (F4)
- `PATCH /penyemaian` kini menolak header ini dengan `400`, sama seperti update lain.
- **Koreksi laporan saya:** hunt-002 menyebut stok reverse sebagai masalah. Itu keliru. Reverse membuat gerakan stok baru, jadi header itu memang boleh; `test/stock-sync.test.js` dan panduan sudah menetapkannya demikian. Perilaku reverse tidak saya ubah.

### Langkah 5: N+1 di daftar panen (F5)
`listHarvests` kini 3 query, berapa pun jumlah barisnya (sebelumnya 102 query untuk 50 baris). `src/features/harvest/store.ts` sekalian ditulis ulang jadi multi-baris. Bentuk respons daftar sama persis dengan respons detail, dan test mengunci hal itu.

### Langkah 6: status HTTP yang konsisten (F6) — mengubah kontrak API
| Kesalahan | Sebelum | Sesudah |
|---|---|---|
| `SOWING_DATE_IN_FUTURE` | `422` | `400` |
| Referensi di body tidak ada (`PENYEMAIAN_NOT_FOUND`, `TABLE_NOT_FOUND`, `TRANSFER_NOT_FOUND` saat `POST`) | `404` | `422` |
| Resource di URL tidak ada | `404` | `404` |

Kode error (`code`) tidak berubah. Saya sudah memeriksa Flutter: status `404` hanya dipakai pada jalur baca detail panen, jadi aplikasi tidak terdampak. Klien lain yang bergantung pada status lama perlu menyesuaikan.

Tiga test lama saya ubah angka statusnya karena mengunci kontrak lama: `test/damage.test.js:94`, `test/harvest.test.js:30`, `test/nursery-remediation.test.js:51`. Hanya angka status yang berubah, tidak ada pemeriksaan yang dilonggarkan.

### Langkah 7: `/health/ready` (F7, T-10)
File migrasi kini dibaca sekali per proses, dan kegagalan baca tidak disimpan. Pemeriksaan status ke database tetap jalan di tiap panggilan, jadi migrasi yang tertunda tetap terdeteksi. Endpoint ini tetap tanpa throttle, supaya probe load balancer tidak tertolak.

### Langkah 8: satu sistem validasi (T-02)
Login dan refresh pindah dari JSON Schema Ajv ke Zod (`src/features/auth/contracts.ts`). Kontrak input sama, dan dikunci 15 kasus batas.

### Langkah 9: pembersihan sesi berkala (T-04)
`src/common/maintenance.ts` membersihkan sesi dan kuota kedaluwarsa saat start dan tiap jam. Kegagalan dicatat tanpa isi error mentah dan tidak mematikan server. Timer dihentikan saat shutdown.

### Langkah 10: tanggal WIB satu tempat (T-11) dan metadata (T-12)
`jakartaDate` kini ada di `src/common/dates.ts`, menggantikan enam salinan di `seed`, `damage`, `nursery`, `transfers`, dan `harvest`. Offset masih tetap UTC+7. Deskripsi `package.json` diperbarui.

### Langkah 11: lapisan database jadi TypeScript (T-01)
- `src/db/client`, `migrate`, `cli`, `harvest-weights` kini `.ts`. `allowJs` dan `checkJs` dihapus dari `tsconfig.json`.
- `parseWeight` dan `formatWeight` pindah ke `src/common/weights.ts`, jadi fitur panen tidak lagi mengimpor dari `db/`.
- Script `db:migrate`, `db:status`, `db:rollback`, `db:backup` kini memakai `--import tsx`.
- `scripts/*.mjs` harus dijalankan dengan `node --import tsx scripts/<nama>.mjs`; catatan ini ada di baris pertama tiap file.
- **Risiko:** `tsx` adalah devDependency. Kalau server produksi memasang dengan `npm ci --omit=dev`, `npm run db:migrate` akan gagal di sana. Repo ini tidak punya konfigurasi deploy, jadi saya tidak bisa memastikannya.

### Di luar rencana: test Flutter yang sudah rusak
`apps/mobile/test/damage_backend_flow_test.dart` gagal sejak commit `5a74723` karena memanggil `POST jenis-inventaris` tanpa `Idempotency-Key`. Saya buktikan gagal dengan alasan yang sama di `HEAD` bersih memakai worktree sementara. Test itu saya tambahi header. Workflow `mobile-ci.yml` menjalankan `flutter test`, jadi kegagalan ini juga akan muncul di CI.

### Dokumen yang diperbarui
`docs/panduan-menjalankan-backend.md`: perilaku seeder, `X-Client-Id` (tertulis "mengabaikannya", padahal sebagian besar endpoint menolak), `expected_version`, dan aturan status HTTP.

## 7. Belum diuji

- Dua penulis serentak di Turso atau multi-instance. Semua test memakai SQLite lokal.
- Shutdown yang rapi: di Windows, `SIGTERM` langsung mematikan proses (`signal: SIGTERM`), jadi penghentian timer saat shutdown tidak terbukti lewat real run. Yang teruji hanya fungsi stop-nya.
- `scripts/deploy-turso-migrations.mjs`, `verify-turso-features.mjs`, `verify-turso-live.mjs`: tidak dijalankan karena menyentuh database remote. Pola impornya sama dengan `reconcile-stock.mjs` yang lulus.
- F7 dan rate limit di balik proxy, TLS, dan konfigurasi produksi.
- Aplikasi Flutter di perangkat nyata. Yang lulus adalah suite `flutter test`.
- Data lama yang sudah rusak: `apps/backend/data/*.db` dan Turso tidak saya sentuh atau periksa.
